# Platform administrator account deletion

Status: implemented in the worktree; local validation and remaining evidence are recorded below. This is not deployment or real-host acceptance evidence.
Branch: `feat/user-account-deletion`. The owner will stage and commit; no Git writes, push, PR, merge or deployment are authorized in this continuation.

## Outcome, authority and limits

A platform administrator explicitly confirms terminal account erasure from the user detail screen. The account ID and row survive for clinical and audit attribution. Personal account fields, password material, external logins, Identity tokens/claims, custom passkeys, temporary links, global roles and tenant memberships are cleared in one Users transaction. Contacts and username become reusable by a different account. Deleted rows are hidden from active queries and cannot be edited or receive credentials/memberships.

The Domain deletion policy refuses self deletion, the last platform administrator, the last owner of **any** clinic, and a missing/stale revision. Application independently authorizes the actor before looking up the subject, then refuses an active session through Authentication's existing port. The owner resolved the sole-clinic-owner gate on 2026-11-01: preserve the existing protection until ownership is transferred, with its own catalogued conflict and tests. The original source map below preceded implementation; no ownership transfer or ownerless clinic was silently introduced.

Do not alter shared API server-error `security.failure` recording, production, secrets, or `src/Hosts/artifacts`. No two-host runner was invoked: its shared fixed ports are reserved by the owner. The browser scenario is written but execution and fresh screenshot inspection remain for the owner's session. No broad clinical/financial/content/communication history purge is part of account deletion.

Repository evidence: root and scoped `AGENTS.md`; `docs/architecture.md`, `docs/codebase-map.md`, `docs/memory.md`, `docs/architecture-rationale.md`; existing account-status handler, role-replacement last-owner protection, UsersManagementAudit/UserAuditChanges, Audit catalog/redaction/writer, Authentication active-session query/final session establishment, and the shared user-management surface. No additional architecture framework or dependency is introduced.

## Owners and implementation boundaries

- **Users Domain:** `User.EraseAccount` owns the terminal account transition and cleared-field projection; `UserDeletionPolicy` decides eligibility from explicit identity/revision/ownership facts.
- **Users Application:** the existing DeleteUser command now has an Application handler. Its real nondeterministic boundaries are an account-erasure transaction port, Authentication's active-session query, the clock and the existing audit writer. The old Infrastructure hard-delete handler is removed. The optional internal revision argument preserves source compatibility; the new public operation requires a revision and Application refuses a missing value on a live account.
- **Users Infrastructure:** derives ownership facts and owns parameterized PostgreSQL locking, one atomic erasure transaction, cache eviction and a persistence guard against stale writes. SQL identifiers come from EF model metadata; caller IDs remain parameters. EF types never enter the new Application ports. Operations on a context are awaited sequentially.
- **Authentication:** final session establishment holds a Users-owned account lease until session commit and final checks. A live directory lookup invalidates pre-issued challenge/handoff subjects. Claims transformation checks user-bearing cookies/validated tokens against authoritative storage, including PATs already issued before deletion. Subjectless client credentials keep their semantics. Existing failed-attempt policy and session compensation remain owned by Authentication.
- **API/Contracts/Audit:** additive named route and operation, typed refusal contract, explicit BrowserOrBearer authentication and ManageAccounts authorization, antiforgery unchanged, application-handled audit, no file transfer. Authorization refusals are recorded without reading subject personal data. Audit owns event/reason/status identifiers; writer enrichment supplies normalized IP and request/correlation metadata. The authorization matrix includes both operation and account-data dispositions.
- **Web:** existing generated mutation and confirmation component; English/Persian resources, destructive confirmation styling, Font Awesome icons and localized tooltips. Success removes target/search query caches and returns to the directory. Refusal, forbidden and unavailable results preserve the editor with localized explanation. Web never decides eligibility.

The Users Application reference to Authentication Application is a narrow port dependency; Authentication Application depends on Users Domain, not Users Application, so the project graph remains non-cyclic. No Users-to-Authentication Infrastructure dependency is added. This was inspected against the architecture matrix; the Main All build passed.

## Concurrency, failure, retry and audit contract

1. Unauthorized actors fail before subject lookup (HTTP 401/403; redacted denied event). A tenant owner is insufficient. Unknown authorized subjects return typed 404 without invented account status.
2. A live account requires its current concurrency stamp. Self/last-admin/last-clinic-owner/stale/active-session refusals return typed 409 and before-to-same status; last-clinic-owner uses a distinct catalogued conflict. The last-owner check covers every owner membership, not just the requesting tenant. Other users' ownership remains intact.
3. Successful deletion is idempotent by subject ID. An authorized repeat returns success, leaves its deletion timestamp/revision unchanged, and records deleted-to-deleted. It does not require the old revision or recheck sessions for a terminal row. The existing audit request key/suffix deduplicates a repeated request ID; new request IDs produce attributable repeat events.
4. PostgreSQL deletion uses a serializable transaction and locks the subject row. Sign-in uses a read-committed lease on that row through session completion. If sign-in wins, deletion waits and then sees the active session; if deletion wins, sign-in waits and sees the terminal marker. PostgreSQL serialization/deadlock or optimistic conflicts become typed concurrency conflicts without automatic mutation retry. Existing general Identity writes retain their configured execution strategy; the spanning erasure/sign-in contexts explicitly use no retry.
5. All Users writes affecting an existing account or its Identity children lock/read the retained row. Deleted subjects reject stale account edits, physical deletion, role/claim/token/credential/link insertion and resurrection. Child-only writes rotate the account revision. This closes stale-registration and stale-role races that a query filter alone cannot close. No concurrent work runs on a shared scoped DbContext.
6. Production user-cache readers and writers are retired: queries read authoritative storage and mutations only evict. This avoids an in-flight reader or mutation repopulating personal data after erasure. Legacy ID/old-name/all-users entries are evicted before identifiers are cleared. Cache failure prevents erasure and propagates; a later attempt can recover. Cache codecs remain only for existing cached-copy compatibility tests, owned by Users; remove them when those legacy-payload tests and supported mixed-version cache consumers are retired. No production Get/Set codec caller remains. Directory reads now incur database load. Before first deletion, drain the existing UserCacheExtensions absolute cache lifetime after retiring the last old-image writer; old normalized-name keys from earlier contact changes cannot be enumerated by IDistributedCache and expire under that existing lifetime. New code never reads or repopulates them.
7. Before commit, cancellation or a persistence failure rolls back the relational transaction and leaves credentials/account state intact. Immediately before commit cancellation is checked; once commit starts it finishes independently of HTTP disconnect, bounded by provider/database timeouts. A lost response is recovered by reloading or repeating the idempotent command. A network failure at commit can be ambiguous: propagate it, record a failed attempt with the known before-state and an unknown (null) after-state, and never claim the account was restored. Scope disposal releases locks and owned contexts, including cancellation while waiting. No shared API error-pipeline change is included.
8. After commit success audit uses a non-request cancellation token. AU-8 behavior is preserved: audit-store failure emits the existing redacted host error/count and does **not** replace deletion's result. Refused audit events are not spooled or replayed. Therefore full event completeness cannot be promised during an audit outage. Audit review remains unavailable if its store is unreadable. No second audit failure recorder is added.
9. Deletion events retain only actor/subject IDs, approved metadata, reason and account status; no erased name, contact, credentials, raw request or prior profile snapshot. Unauthorized/unknown attempts have no fabricated status. Existing historical audit/clinical records remain under their owners' retention policies. Managed immutable strings are not claimed to be physically zeroed; the owned fingerprint byte buffer is explicitly cleared before removal.

## Migration, generation, compatibility and recovery

Canonical generator used after compiling the authoritative model:

```powershell
dotnet ef migrations add UserAccountDeletion --project src/Modules/Users/Infrastructure --context UsersDbContext --no-build
```

Generated migration `20261101074232_UserAccountDeletion` adds only nullable UTC `DeletedAt` to Users' account table. Existing rows remain live and keep their prior enabled state; the migration erases no data. Migration, designer and snapshot were never hand-edited, restored or reconstructed. Historical-schema test models explicitly omit the new property/filter. The generated Down method exists as EF output but **must not be executed**: this is operationally forward-only. Dropping the marker loses terminal-state evidence and cannot restore erased personal data or credentials. No target database, ledger or production schema was changed.

An older image ignores the marker, can list an anonymized disabled row and may repopulate identifiers, enable it or recreate credentials/roles through old management code. Clearing contacts/passwords/passkeys and disabling initially prevents ordinary old-image sign-in, but does not make old management/cached-user code safe. Apply the additive schema before the new app; do not use deletion while any unaware image can handle relevant traffic. After any erasure, rollback to an unaware image is unsupported. Keep the column and use a forward fix or deletion-aware rollback build. Account erasure has no product undo; backup retention and historical clinical records are separate policies.

Main's canonical All build generated OpenAPI into Web's canonical specs. `npm run generate:api` and the focused auth generator regenerated clients through Orval. No generated DTO, client, hook, query key, mock, migration or snapshot was edited by hand. The new Users operation/spec and request/reason enum additions are additive; existing operation IDs are unchanged. Browser clients are ignored build output and remain available locally after generation.

Orval completed with a sandbox-specific `Failed to parse provided mutator function` warning: its native esbuild subprocess cannot start here. Its fallback omits optional request-options parameters, producing existing-caller type errors in clinic/intelligence and older browser specs. Do not patch those generated files or unrelated callers to conceal this. The owner should regenerate in their normal environment and rerun the root browser typecheck before acceptance. The new Users hook, focused owning package/app typechecks, and the new scenario-only browser typecheck pass. The scenario takes forwarding-header fixtures directly from the shared E2E artifact owner; signInHost re-exports that same value for existing consumers, avoiding an unrelated clinic-route dependency in this spec.

No production configuration or dependency/lockfile change is included. Local dependency bootstrap used `npm ci --ignore-scripts --cache .npm-cache --no-audit --no-fund` after native postinstall failed, then the installed HeroUI Pro canonical postinstall used its already cached licensed artifact. Console diagnostics and product validators were not weakened. Temporary source configuration is removed after generation.

Acceptance hot scenarios: last owner in either of two clinics then transfer; sign-in-first/delete-first row locking; concurrent role/credential update; active session across tenants; stale/missing revision; lost-response repeat; cache dependency failure before mutation; post-save rollback/recovery; cancelled lease; deleted OTP/handoff subject, passkey and issued token; release and reuse all contacts under unique indexes; UI cancel/refusal/unavailable/success; audit detail with status-only changes and source IP.

Revision triggers: new User personal/credential fields or Identity child sets; any new account cache/index; a new authentication/session or signed-runtime entry point; changed tenant-owner/role storage; provider change from PostgreSQL; changed audit outage selection; desire to erase clinical/reminder/external-commerce data; mixed-version rollout or rollback after first deletion. Reopen the reference map and concurrency/security proof at the owning boundary when any occurs.
